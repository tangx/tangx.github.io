节约点钱：Magpie 自动路由选择策略

建议点击 查看原文 查看最新内容。

原文链接: https://typonotes.com/posts/2026/11/20/magpie-route-group/

用 AI Agent 做开发时，并不是每个任务都需要最强模型。搜索一个函数、整理文档、写一个简单测试，如果都交给高价模型，花费自然上去了；但一味使用便宜模型，遇到复杂重构或疑难问题，又可能因为反复返工而更费钱。

比较实用的办法，是用 Magpie 的路由组，根据任务特点选择模型：简单任务交给轻量模型，复杂任务再升级。重点不是“每次都选最便宜的模型”，而是让模型能力与任务需要相匹配。

Magpie 路由组如何工作

路由组可以包含多个模型，并按配置的规则为请求选择优先模型。规则通常包含触发条件和目标成员，例如：请求包含图片时选择视觉模型，长上下文任务选择大上下文模型，或根据意图把检索任务交给轻量模型。

带有意图条件的规则，会由路由组配置的意图判断模型对新请求进行分类。规则一般按列表顺序检查；命中后，目标模型成为优先选择，组内其他成员可按路由策略作为后备。意图判断也会带来额外请求，因此应选成本低、响应快且可用性足够的分类模型。

实际触发时机、回退行为、缓存亲和与策略优先级可能受 Magpie 版本和配置影响。上线前建议通过当前版本的路由结果页面确认实际行为，不要只根据规则名称推断。

先用任务标签稳定子进程路由

主 Agent 创建子进程时，子进程的第一条消息通常是主 Agent 写的任务说明。可以在工作流或项目指令中规定统一的开头标签，让意图分类有更清晰的线索。例如：

1
2
3

[文档检索] - 查找 Header 搜索框的数据获取逻辑，并总结相关文件
[写测试] - 为 Header 搜索框补充数据获取测试
[代码审查] - 检查这次改动是否存在回归或安全问题

标签要放在任务开头，后面继续写清楚目标和边界。标签能减少分类歧义，但意图判断仍然是分类，不是精确的字符串匹配，因此不能保证每次都命中。路由组的默认成员和回退顺序也要合理配置，避免分类失败时反而落到不合适的模型。

子进程能否独立命中路由，取决于客户端是否把它作为新的请求发给 Magpie，以及它实际使用的模型名是否指向目标路由组。若客户端允许为子进程配置模型，可以让主进程与子进程使用不同路由组；否则可以先检查 Magpie 的路由日志，确认子进程请求是否进入了预期组。不要假设所有客户端都会自动继承相同的模型配置。

把任务类型与优先级变成模型阶梯

可以先从少量规则开始，再根据实际命中情况调整。下面是一个示例，模型名称和可用渠道需要替换成自己路由组中实际添加的成员：

任务标签适用场景示例模型层级
[文档检索]搜索代码、查定义、收集资料Haiku 或其他轻量模型
[普通]简单问答、单文件小改、格式整理Haiku
[紧急]常规开发、写测试、多文件修改Sonnet
[特急]复杂架构设计、疑难问题、重要代码审查Opus

这只是一个起点，不是固定标准。例如，简单的测试可以交给轻量模型；涉及复杂业务边界的测试，则可以升级给更强的模型。应按照结果质量和返工次数来调整，而不是只看任务名称。

配置时，把更具体、优先级更高的规则放在前面。比如“代码审查”可能同时符合“普通开发”这类宽泛描述，应先配置明确的审查规则，再配置一般任务规则。意图描述尽量清晰、正向、彼此区分，避免在同一条规则里堆很多相似条件。

任务类型和优先级是两个维度

[文档检索]描述的是任务类型，[特急]描述的是优先级。它们并不天然等同于两套可以独立组合的路由开关。如果把多个标签都写成互相独立的意图，规则可能出现重叠，最终由先后顺序决定结果。

最简单的做法是每个子进程只使用一个主要路由标签，并在该标签对应的规则里写清边界。如果确实需要区分组合场景，可以制定明确的组合标签，例如 [特急-代码审查]，并为它配置专门规则；不要指望分类模型总能从多个标签中推断出你心里的优先级。

多个意图怎么写

如果多个描述最终都应该路由到同一个模型，可以在同一条意图描述中写清这些并列场景，例如：

1

请求以 [文档检索] 开头，或主要目的是搜索代码、查找定义、阅读文档和收集上下文。

如果不同场景需要使用不同模型，就分别创建规则，并按优先级排序。路由组界面中的“添加条件”通常用于给一条规则增加组合条件；它与多个规则之间的先后匹配不是一回事。具体的逻辑关系以当前 Magpie 版本的界面说明为准。

并发时别只看模型名称

主 Agent 可能同时启动多个检索子进程。若这些请求都依赖同一个意图判断模型，分类服务的 RPM、并发限制或响应延迟都可能成为瓶颈；分类请求被限流时，结果可能回退到默认模型，而不是按预期分配。

可以考虑：

  • 为路由组配置响应快、成本低且并发能力足够的意图判断模型。
  • 为重要任务准备可用的默认模型和后备成员。
  • 如果需要承接并发，可以配置多个可用账号或渠道；确认路由策略确实会分散请求，或在失败时尝试下一个成员。仅仅添加多个同名模型，不代表 Magpie 一定会自动负载均衡。
  • 检查首位成员的能力。若客户端根据路由组首位模型探测图片或推理能力，首位模型的能力可能影响对应功能是否可用。

一个省钱但不冒进的落地顺序

  1. 建立一个常用路由组，先准备轻量模型、主力模型和高能力模型。
  2. 先添加少数容易区分的规则，例如文档检索、普通任务和复杂审查。
  3. 在工作流中统一子进程标签，让分类模型看到稳定、清楚的任务描述。
  4. 用 Magpie 的路由记录检查命中规则、分类结果和回退路径；若当前版本提供 API 查询，也可按其文档查看请求决策。
  5. 观察实际成本、延迟、限流和返工情况，再调整规则顺序、模型成员与默认策略。

真正省钱的关键，不是把所有任务都塞给 Haiku，也不是只在遇到问题时才切到 Opus，而是让检索、常规执行和高难度判断各自使用合适的模型。先从清晰的标签和少量规则开始，再用真实路由结果迭代，通常比一开始就设计几十条意图规则更稳妥。
