Claude Code 管道用法与模型选择

2026年11月18日
 | 阅读

使用两个模型完成协同代码开发

Claude Code 和 Codex CLI 是负责读写文件、执行命令的 Agent 工具（Harness）；真正负责思考的是它们后端调用的模型。协作流程通常是：一个模型实现需求，另一个模型独立测试和审查，再把问题反馈给实现方修复。

是否有交叉审查的价值，取决于底层模型是否不同，而不只是用了两个 CLI。如果 Magpie 将两个工具路由到不同模型，仍有模型视角的差异；如果路由到同一模型，差异主要来自工具和提示词。使用前应确认模型路由，并遵守代码数据的安全要求。

1. 本地手动交接

适合先验证流程、由开发者手动启动两个工具：

1
2

claude -p "$TASK"                    # 实现需求
codex -q "$REVIEW_PROMPT"            # 运行测试并独立审查

职责应明确：实现方修改业务代码；审查方报告测试结果和问题。修复后再运行测试，确认通过后由开发者检查变更。

2. 自动调用与工具集成

  • Skill 或命令：在开发流程中加入审查步骤，由 Claude Code 调用 Codex CLI。
  • MCP：把 Codex 包装为工具，供 Claude 直接调用。
  • 多 Agent 编排器：负责角色分配、任务派发和结果回传，适合较复杂的协作流程。

选择最简单、便于检查的方案即可；是否使用两个不同的 CLI，不是模型协作的必要条件。

3. 无人值守任务循环

无人值守运行需要预先准备小而明确的任务清单（如 TASKS.md），并为每项任务定义可验证的验收条件。基本循环是：

  1. 实现模型领取一项未完成任务并修改代码。
  2. 审查模型运行测试并检查变更。
  3. 通过后记录结果并领取下一项；失败则将测试输出反馈给实现模型修复。
  4. 达到重试、时间或费用上限后停止，并保留失败日志供人工处理。

在独立分支、worktree 或隔离环境中运行；使用最小必要权限。无人值守不代表应跳过权限和安全检查。

4. 用 GitHub Issue 触发开发

可以由普通脚本或 GitHub Actions 监听带有 ai-todo 标签的 Issue。没有新任务时，只运行轻量的 gh 检查，不调用模型；也可以使用 Webhook 或 Actions 事件触发，避免持续轮询。

以 Issue #100 为例，处理顺序如下：

ISSUE=100
TITLE=$(gh issue view "$ISSUE" --json title -q .title)
BODY=$(gh issue view "$ISSUE" --json body -q .body)
gh issue edit "$ISSUE" --remove-label ai-todo --add-label ai-working
git switch -c "ai/issue-$ISSUE"

PROMPT=$(printf '实现 Issue #%s：%s\n\n需求：\n%s' "$ISSUE" "$TITLE" "$BODY")
claude -p "$PROMPT"

随后由审查模型运行测试并检查分支变更。通过后再提交代码、创建 PR，并更新 Issue 状态；失败则反馈报告，让实现模型修复。

5. 有上限的修复循环与收尾

为每个 Issue 设置最大重试次数。审查模型应使用明确的成功标记，例如只在全部测试通过时输出 TEST_PASSED，避免把普通日志中的 “PASS” 误判为成功。

1
2
3
4
5

重复至多 MAX_RETRIES 次：
  获取测试与审查结果
  若结果明确为 TEST_PASSED：创建 PR，标记 ai-done，然后结束
  否则：把报告交给实现模型修复，再次验证
若仍未通过：标记 ai-failed，保存日志并停止

领取任务时先将标签改为 ai-working，避免重复处理；每个 Issue 使用独立、干净的 Agent 进程，避免上下文不断累积。将 Issue 内容视为不可信输入，并限制自动化环境可访问的代码、凭据和操作范围。

总结：轮询本身不消耗大模型 Token，真正产生模型调用的是处理任务和修复；事件触发、独立任务上下文、重试上限和权限隔离，有助于控制费用并降低自动化风险。
